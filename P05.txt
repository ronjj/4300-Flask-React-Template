P05
===


IMPROVEMENTS STATEMENT

IR (Information Retrieval)

Since the first prototype our IR layer has moved from a narrow keyword/boolean matcher to a layered pipeline that combines tokenized filtering, TF-IDF style scoring and a semantic router. In P03 our "search" was essentially a regex-and-rules filter in player_search.py: we matched league names, nationalities, positions, and a hand-written list of adjectives, then returned whatever survived the filter, ordered by a single hard-coded sort key (usually goals). In P04 we layered TF-IDF cosine over the player text corpus on top of this filter so description-style queries ("creative midfielders", "clinical finishers") would rank by language similarity rather than raw counts, but the boolean filter still acted as a gate and as the final sort.

Between P04 and P05 we rewrote the orchestration in src/search_service.py so that the baseline boolean/TF-IDF path is no longer the last word. Every query is now routed into one of three handlers (named-player similarity, description similarity, or a generic boolean-plus-semantic reranker) and in every branch the semantic prototype is the authoritative ranker. The boolean stage is now used only to build a candidate pool (capped at 4,000 rows) that the vector models then re-rank; keyword hints like "top scorers" or "best" no longer pin the final order. This directly addresses the TA metareview point that "ranking conflicts likely stem from your baseline regex and Boolean filtering rules overriding your new semantic models" - the hardcoded keyword weights were reduced to zero for final ranking, and kept only as filters/prototype seeds. It also fixes the symptom the TA flagged ("top scorers in La Liga" and "top scorers in Premier League" returning the same list): each query now produces a different candidate pool and a different semantic prototype (feature-aligned unit vector when the sort concept matches a canonical feature, exemplar-weighted centroid otherwise), so the two queries can no longer collapse to the same ranking.

SVD

In P03 we had no latent model at all. In P04 we introduced a TruncatedSVD fit over our scaled player feature matrix (embeddings/build_svd.py) and compared raw-feature cosine against latent-space cosine, but the integration was fragile: SVD only activated for description-style queries, the latent columns were referred to as "dim 0"/"dim 1", and we never showed the query's own activation on a dimension, only the players'. That is exactly the problem the TA metareview called out ("SVD results only sometimes show up... the SVD dimensions are unnamed and it seems to not show the SVD dimensions of the query").

For P05 we fixed all three points. First, search_service._dual_semantic_search is now invoked on every branch that has an embedding bundle - named-player similarity, description similarity, and the general boolean path (search_service.py around line 443). As long as svd_bundle.joblib is loadable, every search now returns both results_without_svd and results_svd plus a svd_latent_dimensions legend, so the SVD comparison column is no longer "sometimes missing." Second, we wrote _dimension_human_label and _component_feature_hints in embeddings/svd_search.py that inspect the top positive and negative loadings of each component and map them onto a fixed bucket dictionary (Finishing, Chance creation, Passing and progression, Ball carrying, Defending, Usage/availability, Discipline, Goalkeeping, Position bias). Each latent dimension is now surfaced to the frontend with a human label ("Finishing + Chance creation"), a "High vs Low" detail string, and its explained-variance ratio. Third, explain_latent_alignment now emits both query_activation and player_activation per dimension along with the signed contribution to the cosine, and the frontend renders both sides in the SVD panel so the user can see why the query and the player land on the same axis (or why they don't).

RAG

P03 had no RAG - the "chat" was a free-form LLM call with no grounding. P04 added a first-pass RAG: we packed the top boolean-search rows into a single prompt and asked the LLM to answer. It worked for well-formed queries but hallucinated stats when the boolean filter returned the wrong players and gave no signal when retrieval confidence was low.

For P05 we split the RAG path into its own package at src/retrieval/ with four stages: query_understanding.py normalizes the message into filters (positions, leagues, era, style, comparison targets, similarity anchor, max-age constraints), retrieve.py runs a filter-plus-semantic reranker over PLAYER_INDEX with a confidence score (with rewrite/warn/min-accept thresholds at 0.55/0.40/0.30), evidence.py serializes only the stats the LLM is allowed to cite, and generate.py wraps the prompt with a strict "read-before-write" contract (every candidate sentence must include at least one stat copied verbatim from that candidate's key_stats). The prompt also distinguishes anchor vs candidate evidence for similarity queries and tells the model to return the 3-5 strongest available matches rather than reject everything, which was a failure mode in the P04 version. Although the TA metareview did not list RAG issues, we mention these changes because the same ranking fixes we made for IR/SVD feed the RAG retriever, so improvements in search quality propagate directly into the chat answers.


CLASS CONCEPTS USED

- Tokenization / text normalization. player_search.normalize_text is the shared tokenizer/normalizer used by every other stage (boolean filters, embedding lookup, RAG query understanding) so strings like "Vinicius Jr." and "vinicius jr" collapse to the same key.

- Boolean retrieval. boolean_search in player_search.py applies league / nationality / position / era / age filters to build a candidate pool. In P05 this is used as a recall stage, not as the final ranker.

- TF-IDF and cosine similarity. Used both over player-description text (embeddings/text_embeddings.py) and over the engineered feature matrix. sklearn.metrics.pairwise.cosine_similarity is the scoring function in embeddings/similarity.py, embeddings/svd_search.py, and the reranker inside search_service._dual_semantic_search.

- Term-document style matrix. The player x feature matrix in embeddings/player_embeddings.npy is the structured analogue of a term-document matrix: each row is a "document" (player), each column a "term" (stat or one-hot position) with standardized weights from position_scalers.joblib.

- Query expansion / prototype construction. For non-named queries we build a prototype vector by (a) aligning to a canonical feature unit vector when the sort concept matches (e.g., goals, assists, progressive_passes), or (b) taking a weighted centroid of exemplar players (e.g., the 50 best set-piece scorers for freekick_score, the 50 best dribble+pass creators for tekky_score). This is the same idea as Rocchio/centroid query refinement applied at query time rather than as a relevance-feedback loop.

- SVD (TruncatedSVD). Fit once offline in embeddings/build_svd.py; at query time we call svd.transform on the prototype and on every candidate, renormalize, and compare both raw-feature cosine and latent cosine (rank_raw_vs_svd). The explained-variance ratios and component loadings are both exposed to the UI.

- Latent semantic interpretation. _dimension_human_label maps the top loadings of each SVD component onto a small dictionary of football concepts (Finishing, Chance creation, Defending, etc.) to give every latent axis a human name - this is how we address the "unnamed dimensions" feedback.

- Named-entity lookup / approximate string match. find_player_by_name normalizes, strips accents, and does substring + fuzzy fallback before handing the match to the similarity models.

- RAG (Retrieval-Augmented Generation). Implemented as a discrete retrieve-rerank-ground-generate pipeline in src/retrieval/. Retrieval reuses the same TF-IDF + SVD stack so the chat and the search page stay consistent.

- Evaluation thresholds / confidence scoring. In retrieve.py we compute a retrieval confidence score and use the three thresholds (RETRIEVAL_CONFIDENCE_REWRITE_THRESHOLD, WARN_THRESHOLD, MIN_ACCEPT) to decide whether to rewrite, warn, or reject a query - a direct application of the evaluation-metric material from class.


QUALITATIVE EVALUATION

Example inputs we used to verify the P04 -> P05 improvement:

1. "best Spanish goalkeepers" - P04 returned an alphabetical list of Spanish GKs because the boolean filter selected by nationality + position and then sorted by the default key (goals), which is roughly 0 for every GK, so ties broke on name. In P05 the boolean stage still filters the candidate pool, but the prototype becomes a GK-aware unit vector blended with the save-related feature columns (saves, clean_sheets, save_percentage), and the SVD reranker promotes keepers whose latent profile aligns with the Goalkeeping bucket. The top row is now a high-minute, high-save keeper rather than whoever's name starts with "A."

2. "top scorers in La Liga" vs "top scorers in Premier League" - P04 often returned overlapping results because the ranking function was the same (goals desc) and the boolean filter was too permissive on multi-league players. In P05 each query builds its own candidate pool (league filter is strict on p.league == "La Liga" / "Premier League"), the prototype is the unit vector for goals, and the final output shows distinct leagues in the league field of every hit because we propagate the filter onto the returned cards (hit["league"] = league in search_service.py).

3. "players like Vinicius Jr" - This is the named-similarity path. The query is matched by SIMILAR_PLAYER_PATTERNS, Vinicius is resolved via get_player_index, his embedding row is used as the prototype, and _dual_semantic_search returns a raw cosine column and an SVD column side by side. Each SVD hit now carries an svd_explain payload with named dimensions ("Ball carrying / 1v1 + Chance creation"), query activation, player activation, and the signed contribution - none of which existed in P04.

4. "creative midfielders from Argentina under 23" - description-style query. P04 routed this through TF-IDF on the text corpus only; P05 also applies the filter set (primary_position == Midfielder, nationality_region = Argentina, max_age_under = 23) and then builds a description prototype via build_description_prototype, which blends the exemplar midfielders' embedding vectors weighted by style match. The SVD column then reranks with named latent dimensions so the user can see which creative axis the player scores on.

5. RAG comparison ("compare Bellingham vs Pedri") - P04 sometimes answered without citing any stat because the model declared the evidence "insufficient." P05 uses the direct-comparison pattern in query_understanding.py, resolves both anchors, attaches their key_stats as separate evidence blocks, and the system prompt in generate.py enforces that every sentence about a player contains at least one stat from that player's key_stats.

Screenshots comparing P04 and P05 outputs for each of the five examples above live in assets/p05/ (to be attached alongside this document).


KNOWN ISSUES

1. Cold-start SVD labels are generic for low-variance dimensions. For components beyond roughly dim 10 the explained variance drops below 1% and the top loadings are noisy, so the human label can collapse to "Latent factor" or a single bucket. We currently cap the legend at 16 dimensions but the later ones carry limited interpretive value. (Feedback requested: is a smaller n_components (e.g. 8) acceptable for the UI if we show the full 16 only in a debug view?)

2. Description prototype depends on the quality of the "exemplar" set. For rare styles (e.g., "press-resistant deep-lying playmakers") fewer than a dozen players match the initial filter, and the centroid is dominated by one or two outliers. We fall back to the feature-aligned unit vector in that case, but the fallback loses the stylistic nuance. (Feedback requested: is centroid + fallback acceptable, or should we switch to a k-NN-in-latent-space seed?)

3. RAG confidence is a single scalar. retrieve.py returns one confidence number and applies three thresholds; it does not separate filter confidence from semantic confidence. A query that filters cleanly but matches weakly is treated the same as a query that filters poorly.

4. Text embeddings are only computed for players who appear in our Wikipedia/Reddit corpus. Players who are in the statistical feature matrix but absent from the text corpus get a zero text vector, which biases description-style queries toward well-documented stars. We would like feedback on whether to back-fill with a club/league prior or leave the zero vector and rely on the structured features.

5. Latency spikes on very broad queries. With no league/position filter the candidate pool hits the 4,000 cap and the SVD transform dominates the request time (around 800 ms warm). This is still under our target but is close to the edge on cold-start.


FEEDBACK FROM TA ON P04 (for reference and tracking)

"This project has improved significantly, however there are currently some issues with the live implementation. Overall you lost two points, one for SVD not always working and being incomplete, and one for general search issues. For the first issue with SVD, it seems as though the SVD results only sometimes show up with some of the suggested search results. Additionally, for the results that do have SVD, the SVD dimensions are unnamed and it seems to not show the SVD dimensions of the query. For the second issue, the general search doesn't seem to return very good results. For example, one suggested query 'best Spanish goalkeepers' seems to simply return Spanish goalkeepers in alphabetical order rather than sorted by who is best. Furthermore, many queries seem to return the same exact results, such as 'top scorers in La Liga' and 'top scorers in Premier League'. The search issues may be stemming - Recommendation: these ranking conflicts likely stem from your baseline regex and Boolean filtering rules overriding your new semantic models. Consider significantly reducing the weight of these hardcoded keywords, or removing them entirely, to ensure your embedding-based similarity searches can route and rank correctly."

How each point is addressed in P05:

- SVD only sometimes shows up -> Fixed. search_service._dual_semantic_search is invoked on every branch whenever svd_bundle.joblib loads; results_svd is populated for named-similarity, description, and boolean queries.

- SVD dimensions are unnamed -> Fixed. embeddings/svd_search._dimension_human_label and svd_dimension_legend map each component's top loadings to named football buckets (Finishing, Chance creation, Defending, etc.).

- Query's own SVD dimensions not shown -> Fixed. explain_latent_alignment now returns query_activation alongside player_activation and the signed contribution; the frontend renders both.

- "Best Spanish goalkeepers" returned alphabetically -> Fixed. Prototype construction now uses a GK-aware feature vector and the SVD reranker, not the default goals sort.

- Duplicate results across distinct queries ("top scorers in La Liga" vs "... Premier League") -> Fixed. Strict league filter is applied before the semantic stage, and filter metadata (league/position) is propagated onto every returned card.

- Hardcoded keywords overriding semantic models -> Fixed. The boolean / keyword layer is now a candidate-pool stage only; final ranking comes from raw and SVD cosine over the embedding matrix. Keyword weights on final rank are effectively zero.

As noted by the TA: "There's no issues with the system as of right now." We interpret that as a green light on the live deployment and focus this P05 writeup on documenting the changes that produced that outcome.
